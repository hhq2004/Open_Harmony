# P07 预加载与预渲染优化

本仓库用于“基于用户热点触达路径预测的预加载 / 预渲染优化”课程项目。现阶段提供团队共享接口、独立的一阶路径预测基线，以及可在 Windows 或 Linux 上执行的本地开发 pipeline。正式要求见 [target.md](docs/target.md)。

当前检查覆盖 TypeScript 核心逻辑。它不生成鸿蒙应用包，也不代表预加载、视图预渲染、系统空闲判定或设备性能验证已经完成。最终的系统、SDK/API、设备及 ArkTS 接入方式需在目标环境确定后落实；TypeScript 编译通过不能证明 ArkTS 或鸿蒙编译通过。

## 运行

使用 Node.js 22 与 npm。在仓库根目录执行：

```powershell
npm ci
npm run pipeline
```

pipeline 依次执行环境检查、严格类型检查、编译、单元测试和合成路径回放。编译前清理本项目生成的 `dist/`，避免已删除源码的旧产物让检查误通过；不会清理历史运行证据。任一步失败立即停止后续执行，并返回非零退出码。每次产生独立的 `artifacts/pipeline/<run>/` 目录，包含 JSON 报告和各步标准输出、错误输出，不覆盖历史记录。

也可以分别执行：

```powershell
npm run doctor
npm run typecheck
npm test
npm run replay
```

`doctor` 对鸿蒙工具的检测范围是命令路径，不能据此判断设备已连接或 SDK 已配置正确。鸿蒙工具未就绪不会阻止独立算法检查，报告会明确保留目标环境待办。

## 五条协作任务

下面是按模块划分的工作入口，不包含姓名绑定；团队再确定实际负责人。

| 工作入口 | 接口或目录 | 第一轮交付 |
| --- | --- | --- |
| 工程集成与演示应用 | `src/contracts.ts`，目标应用工程待建立 | 固定环境、最小可运行应用、公共接口评审与集成 |
| 行为数据与路径预测 | `VisitCollector`、`PathPredictor`，`src/prediction/` | 采集脱敏及开关、同会话事件接入、预测模块与离线评测；采集与预测可分别实现 |
| 空闲调度与数据预取 | `PreloadScheduler` | 空闲触发、任务优先级、预取、取消与异步结果处理 |
| 视图预渲染与回收 | `ViewPreparer`、`PreparedView` | 可验证的视图预构建与复用、失效释放、内存压力回收 |
| 测量与质量 | `MeasurementSink`，`tests/`、`benchmarks/` | 真实基线、路径回放、异常验证、原始数据与证据汇总 |

当前实际实现只有 `MarkovPredictor`；其余是待评审的逻辑契约，并非已实现的鸿蒙 API。采集适配器只把同会话内相邻事件交给预测器，不跨会话串联。

调度侧负责取消任务，资源侧负责释放已经创建及取消后晚到的资源。`PreparedView.dispose()` 应可重复调用，`take()` 成功后由调用者持有并释放该资源；这些生命周期规则仍需在真实实现中验证。

## 预测基线与测试数据

一阶基线按页面转移频次输出候选。未知页面不预测；相同频率按页面标识确定顺序。分数是条件频率，截取前几个候选时不重新归一化，不能将其直接称为已校准的置信度。当前基线还没有持久化、容量治理或个性化策略。

`benchmarks/fixtures/synthetic-sessions.json` 是明确标记的合成数据，只用于连通 pipeline。回放时先预测再观察真实下一跳，按会话隔离；训练数据在评测之前提供，评测过程中逐步在线更新。报告同时给出预测覆盖率、全体机会命中率和有预测时命中率，分母为零时返回 `null`。

这些数字不能写成真实用户命中率、点击加速或内存优化结果。后续应以经过脱敏的真实路径和固定目标环境建立单独评测。

## 协作与后续接入

每项任务记录接口、依赖、验收步骤和交付证据。开发使用独立分支，合并前运行 `npm run pipeline` 并由另一名成员检查接口或行为；主线保持可执行。文档由模块实现者同步维护，评测负责人汇总证据。

远程协作平台已选定 GitHub，工作流位于 [.github/workflows/host-pipeline.yml](.github/workflows/host-pipeline.yml)。推送代码、提交或更新 PR、手动触发时，在 Windows 与 Ubuntu 两个环境分别安装锁定依赖并运行本地同一条 pipeline。工作流使用固定提交的官方 Actions，并缓存 npm 下载内容。已生成的运行报告在检查成功或失败后均尝试归档，保留 14 天。

目前 GitHub 仓库尚未创建，工作流文件仅在本地准备好，云端尚未运行。创建仓库后，应将当前 `OpenHarmony_project` 的内容作为仓库根目录，确保 `.github/`、`package.json` 和 `package-lock.json` 位于根目录；不要把外层整个 `hong_meng` 工作区作为这个项目仓库上传。

首次推送后，在 GitHub 的 Actions 页面检查两个系统的运行结果，并下载各自的 `host-pipeline-*` 报告。确认实际检查名称后，可由仓库管理员为主分支设置 PR 审查与必需状态检查。这些远程设置尚未执行，五人的实际权限也需在仓库创建后分配。

目标环境确定后再增加应用包构建、安装启动、真实预渲染/取消/回收集成测试和设备评测。这些步骤在当前报告中列为 `not-run`，不能用合成回放或 GitHub 的主机侧检查代替。

现有课程材料和两份官方模板保留在 `docs/`。依赖、编译输出和运行证据已设置 Git 忽略规则，原始参考切片也单独忽略以避免嵌套 Git。
