## 六、建议的集成与合并流程

1. **冻结基线并收集交接。**以当前 `origin/main` 为合并基线，确认 A/B/C 的 `VisitEvent`、会话边界、`PreloadTarget` 和资源所有权；让 C/D/E 分别核对其接口使用方式，记录问题及负责人。
2. **准备 A PR。**由 A 分支提交本报告后推送 `codex/a-application-integration`，向 `main` 开 PR。PR 只应包含 A 应用、演示、同步脚本、测试及说明，外加 `src/preload/scheduler.ts` 的兼容性小改动；该 C 文件必须请 C 负责人审阅。不要提交 `artifacts/`、D 盘构建副本或未签名 HAP。
3. **PR 检查。**在 PR 上要求 Windows/Ubuntu Host pipeline 通过；合并人本地复核 `npm run pipeline`、`npm run build:harmony` 和 `git diff origin/main...分支`。目前主机检查为通过，A 的云端检查尚未产生，不能预填“通过”。
4. **合入 A 后复核。**更新主分支，重新跑主机流水线和 HAP 构建，检查浏览器演示、采集默认关闭/清除、同会话一次投递、预测命中/落空以及取消后的资源归属。将版本、检查链接和异常情况登记在 `submission/evidence/integration/`。
5. **平台联调分批 PR。**先由 A/C 提交真实数据源、可取消请求和可靠环境信号；再由 C/D 提交 ArkUI 视图准备、命中移交和清理；最后由 A/E 接入设备测量并保存脱敏原始数据。每批 PR 均要求上下游评审和对应异常场景证据。不存在必须再次合入旧 C 分支才能开展这些工作的前提。
6. **最终验收。**明确目标 OpenHarmony 设备或等效运行环境、签名与安装方式，验证完成、取消、失败、落空、晚到资源及内存压力；E 在相同设备和场景下比较基线与优化。按 [最终提交清单](../submission/README.md) 补正式设计文档、演示视频或 PPT、版本和证据。若课程最终允许仅以主机复现验收，应先取得课程要求的明确口径，再按实际范围标注。
