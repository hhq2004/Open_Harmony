4.3 进程、线程与调度

4.2 结尾留了一个问题：任务挂到就绪队列之后，谁来选中它执行？这一节讲调度器。它每次被唤醒只做两个决定：选谁（下一个跑哪个任务）、何时换（什么时候重新选）。

三种内核的目标完全不同：RTOS 追求确定性——最坏情况必须在预期之内；Linux 追求公平与吞吐——长期看每个任务拿到应得的份额。目标不同，数据结构就不同：LiteOS-M 用位图 + 32 条链表换 O(1)；Linux 用红黑树换公平。

本节从 LiteOS-M 的源码切入（结构最简单、最能看清调度本质），再对照 LiteOS-A 的两级队列与 Linux 的 CFS/EEVDF。

先更正原页面的两处错误

这一节的原版内容有两处会误导人的地方，如果你之前读过，请以本版为准。

⚠️ ① 优先级数量写错了。原文写「256 优先级抢占」。LiteOS-M 实际是 32 个优先级（0~31，0 最高）。那个 256 是 LOSCFG_BASE_CORE_TSK_LIMIT（最大任务数），把「任务数上限」误当成了「优先级数」。
⚠️ ② 位图置位方向反了。原文写 g_queueBitmap |= 1 << priority，实际是 PRIQUEUE_PRIOR0_BIT >> priority（0x80000000 右移）。方向反了，CLZ 取到的就是反过来的优先级——最高优先级会被当成最低。下一张卡专门讲这个。

先把六个词说清

调度这一节的困惑，多半来自名词混用（尤其「进程/线程/任务」）。先把词定死。

术语含义在 LiteOS-M 上成立吗
任务 / 线程CPU 调度的最小单元，有自己的栈和寄存器现场✅ 只有这个
进程资源的归属单元：独立地址空间、文件描述符表❌ 不存在
优先级数字越小越优先（RTOS 惯例）。决定「谁能抢占谁」✅ 0~31
就绪队列「已具备运行条件、等 CPU」的任务待的地方。不包含正在跑的✅ 32 条链表
时间片同优先级任务轮流跑，每次最多跑多久✅ 可配置（默认 10 tick）
抢占高优先级任务一就绪，立刻打断正在跑的低优先级任务✅ 抢占式
📌 一条容易记混的规则：优先级只在「不同优先级」之间生效，时间片只在「同优先级」之间生效。两者不是二选一，而是分层配合——先比优先级，同优先级才轮转。

三种内核，三种调度实体

内核调度单元优先级范围选择依据
LiteOS-M任务（等价线程）0~31，0 最高最高优先级 → 同级时间片轮转
LiteOS-A线程（进程是资源容器）进程 0~31 / 线程 0~31，静态进程优先级 + 线程优先级两级
Linuxtask（线程）nice −20~19 映射权重vruntime / 虚拟截止时间
💡 一个反复出现的概念：三种内核调度的最小单元都是「线程」，不是「进程」。进程只是资源的壳——这条在 LiteOS-A 和 Linux 上完全一致，在 LiteOS-M 上则干脆没有进程这个概念。

LiteOS-M 就绪队列：源码级

整个调度器最核心的数据结构只有两个变量：一组链表和一个 32 位整数。

// kernel/include/los_sched.h #define OS_PRIORITY_QUEUE_NUM 32 #define PRIQUEUE_PRIOR0_BIT 0x80000000U // 最高位 = 优先级 0 LOS_DL_LIST *g_priQueueList = NULL; // 32 条就绪队列（每条对应一个优先级） UINT32 g_queueBitmap; // 32 位位图：哪条队列非空 // 入队：队列本来为空时才置位（避免重复置位） VOID OsSchedPriQueueEnQueue(LOS_DL_LIST *item, UINT32 priority) { if (LOS_ListEmpty(&g_priQueueList[priority])) { g_queueBitmap |= PRIQUEUE_PRIOR0_BIT >> priority; // ← 右移，不是左移 } LOS_ListTailInsert(&g_priQueueList[priority], item); } // 取最高优先级任务：一条 CLZ 指令搞定 LosTaskCB *OsGetTopTask(VOID) { if (g_queueBitmap != 0) { UINT32 priority = CLZ(g_queueBitmap); // 前导零个数 == 优先级 return LOS_DL_LIST_ENTRY(g_priQueueList[priority].pstNext, LosTaskCB, pendList); } return OS_TCB_FROM_TID(g_idleTaskID); // 全空 → 跑空闲任务 }
📌 版本差异提醒：不同 OpenHarmony 版本里，这个函数可能在 kernel/src/los_priqueue.c（叫 OsPriQueueEnqueue），也可能在 kernel/src/los_sched.c（叫 OsSchedPriQueueEnQueue）；位图变量也可能写作 g_priqueueBitmap。结构完全一致，改名不改逻辑，看到不同名字不要以为找错了。

位图的方向：为什么必须「右移」

这是本节最容易写错、也最难自查的一处。位图的最高位必须对应优先级 0，因为 CLZ（Count Leading Zeros，统计前导零）返回的是「从最高位数起有几个 0」，它必须直接等于优先级。

priority: 0 1 2 ... 30 31 │ │ │ │ │ bit: 31 30 29 ... 1 0 (MSB) (LSB) // 优先级 0 和 29 都有就绪任务 g_queueBitmap = 0b10000000_00000000_00000000_00000100 ↑ ↑ prio 0 就绪 prio 29 就绪 CLZ(0x80000004) = 0 → 选优先级 0 ✅ CLZ(0x00000004) = 29 → 选优先级 29 ✅
写法位图值（prio 0 就绪）CLZ 结果
1 << 0（原页面写法）0x0000000131 ❌ 把最高优先级当成了最低
0x80000000 >> 0（正确）0x800000000 ✅
⚠️ 另外注意 OsGetTopTask 里的 if (g_queueBitmap != 0)：CLZ(0) 在 C 里是未定义行为（不同架构返回值不同），所以必须先判空再调用。bitmap == 0 说明一个就绪任务都没有，此时切到空闲任务。

O(1) 到底省在哪：与红黑树的对比

「O(1) 选取」不是营销词，它意味着调度耗时与任务数量无关——这对实时系统是硬指标。

操作LiteOS-M（位图 + 链表）Linux（红黑树）
选最高优先级1 条 CLZ，O(1)取树最左节点，O(1)（缓存）；EEVDF 下是 O(log n)
插入就绪尾插链表，O(1)插入红黑树，O(log n)
出队摘链头，O(1)删除节点，O(log n)
能否表达「公平」❌ 只有优先级，无权重概念✅ vruntime 精确记录每个任务跑了多久
⚡RTOS 的选择
32 条队列 + 32 位位图，结构极简、内存极小、最坏情况可算。代价是只能表达「谁更重要」，不能表达「各占多少」。
🌳Linux 的选择
红黑树按 vruntime 排序，能精确做加权公平。代价是每次调度有 O(log n) 开销，对 MCU 太重。
💡 一句话总结这条取舍：实时系统优化「最坏情况」，通用系统优化「长期公平」。前者不能容忍「偶尔慢一次」，后者不能容忍「某个任务永远饿着」。

任务状态与时间片

LiteOS-M 用 taskStatus 的位标记表达状态，一共定义了 12 个标志位。真正需要掌握的是下面 5 个核心状态。

状态标志什么时候进入
就绪 READYOS_TASK_STATUS_READY创建完成，或从阻塞/挂起被唤醒，挂在就绪队列里
运行 RUNNINGOS_TASK_STATUS_RUNNING被调度器选中。注意：它同时仍在就绪队列中
阻塞 PENDOS_TASK_STATUS_PEND等信号量/互斥锁/队列/事件——被动等待资源
延时 DELAYOS_TASK_STATUS_DELAY调了 LOS_TaskDelay——主动让出 CPU
挂起 SUSPENDOS_TASK_STATUS_SUSPEND被别的任务 LOS_TaskSuspend 强制停下，不是自己愿意
┌────────── 被唤醒 / 超时 ──────────┐ ↓ │ [创建] ──► READY ──被选中──► RUNNING ──等资源──► PEND ↑ │ │ │ │ │ └──主动延时──► DELAY └──被抢占/时间片耗尽┘ └──LOS_TaskSuspend──► SUSPEND │ Resume ─────┘ // 关键：被抢占后回到 READY，不是"取消"； // 只有 PEND/DELAY/SUSPEND 才真正离开就绪队列

时间片的两级策略（一个容易被忽略的优化）

场景插入位置为什么
剩余时间片 > 最小值队列头它还没跑完，让它继续跑——避免无谓的切换开销
时间片已耗尽队列尾 + 重置时间片同优先级公平轮转
📌 两个配置项要分清：LOSCFG_BASE_CORE_TIMESLICE 是总开关（某些产品的默认配置里是关闭的，即纯抢占不轮转）；LOSCFG_BASE_CORE_TIMESLICE_TIMEOUT 是时间片长度（常见 10 tick）。开了总开关才会有轮转——排查「同优先级任务饿死」时先查这里。

什么时候会触发一次调度

调度不是随时发生，也不是每个 tick 都切换。触发点只有四类。

1
高优先级任务就绪
中断里释放了信号量、或创建了高优先级任务 → 立即抢占当前任务。验收：能说出「抢占发生在哪个时刻」。
2
当前任务阻塞
等锁、等队列、延时 → 从就绪队列摘除，立刻选下一个。验收：能区分 PEND 与 DELAY 的主动权归属。
3
时间片耗尽
仅在同优先级存在其他就绪任务时才切换。这是「同优先级公平」的唯一来源。
4
显式调用
LOS_Schedule() 主动让出；LOS_TaskYield() 让给同优先级。验收：知道 yield 不会让给更低优先级。
⚠️ 两个禁区：① 中断服务程序里不能阻塞（不能等锁、不能延时），否则调度器无法推进；② 系统启动初始化阶段不允许触发调度，此时就绪队列还没建好。
💡 还有一个开关值得知道：LOS_TaskLock / LOS_TaskUnlock 可临时禁止调度（不是关中断）。适合极短的临界区——比关中断的副作用小，但仍会推迟所有任务的响应。

优先级反转：RTOS 最著名的坑

这是调度这一节唯一必须掌握的「故障模式」。它不是理论问题——1997 年火星探路者号就因为它在火星表面反复重启。

// 三个任务：H 高 / M 中 / L 低，共享一把锁 t0: L 拿到锁，进入临界区 t1: H 就绪，抢占 L，但 H 也需要这把锁 → H 阻塞 t2: M 就绪（不需要锁），优先级高于 L → M 抢占 L t3: L 拿不到 CPU，锁一直不释放 → H 无限期等待 // 结果：H 明明优先级最高，却被 M 一直压着。 // 优先级"反转"了 —— 实际执行顺序变成 M > L > H // 火星探路者：H 是总线管理任务，超时触发看门狗 → 整机复位
方案做法优点代价
优先级继承
PIP		高优先级任务等锁时，持锁者临时提升到等待者的优先级按需提升，影响面小；实现相对简单可能链式继承（A 等 B、B 等 C）；不防死锁
优先级天花板
PCP		每把锁预设「天花板」= 可能用它的最高优先级；一拿锁就提升到天花板阻塞时间有严格上界；可防死锁需要静态分析出天花板值；可能过度提升
禁止抢占持锁期间不许切换任务零额外开销，最简单阻塞所有无关任务，只适合极短临界区
💡 LiteOS 的互斥锁（LOS_Mux*）默认带优先级继承，而信号量（LOS_Sem*）不带。这条区别很实用：保护共享资源用互斥锁，不要用信号量代替——用信号量做互斥就是把优先级反转的门开着。
📌 但优先级继承不是万能的：它只解决「持锁者被中优先级任务抢占」，不解决临界区本身太长。如果临界区跑了 10ms，再好的协议也救不了实时性。设计上的第一原则永远是缩短临界区。

LiteOS-A：两级队列

LiteOS-A 有真正的进程，于是队列也变成两级。这是它和 LiteOS-M 最大的结构差异。

进程优先级桶队列（32 个，0~31） │ ├─ [prio 0 ] ──► 线程优先级队列组（32 个线程优先级） ├─ [prio 1 ] ──► 线程优先级队列组 ├─ ... └─ [prio 31] ──► 线程优先级队列组 │ └─ [线程 prio 0] ─► 同优先级线程按时间片轮转 [线程 prio 1] ... // 调度单元是线程；进程优先级决定"在哪一组里找线程"
特性LiteOS-A
调度策略进程仅 SCHED_RR；线程支持 SCHED_RR 与 SCHED_FIFO
优先级静态优先级，不能动态调；进程/线程均为 0~31（用户态进程可配 10~31）
tickless内建：没有即将到期的事件时不产生周期 tick 中断，省电并减少无用中断
空闲队列全空时选 KIdle 进程的线程
⚠️ 别把 LiteOS-A 的「进程优先级」当成 Linux 的 nice：它只支持静态优先级，跑起来不能改；而且进程调度策略只有 SCHED_RR，没有 Linux 那套 CFS/EEVDF。写移植代码时如果依赖动态调优先级，到这里会失效。

Linux：从 CFS 到 EEVDF

这一条和 4.1 的选型直接相关——OpenHarmony 同时维护 5.10 和 6.6 两条 Linux 基线，它们的调度器不是同一个。

方面CFS（≤ 6.5）EEVDF（6.6+）
选取规则vruntime 最小的任务（红黑树最左节点）合格任务里虚拟截止时间最早的
公平性靠什么vruntime 长期收敛引入 lag（欠/超份额）：只让 lag ≥ 0 的任务参与竞争
延迟敏感任务靠唤醒抢占等启发式，效果不稳请求短时间片 → 更早的虚拟截止时间 → 更快被选中
数据结构每 CPU 一棵红黑树仍是红黑树，增加截止时间维度的缓存
时间片由 sched_latency 等参数隐式推导显式，主旋钮 sched_base_slice_ns（默认 3ms）
📌 关键点：EEVDF 不是把 CFS 推倒重来——vruntime、权重表、红黑树、cgroup 全都沿用，被替换的只是「从树里挑哪个」这个决策规则。所以在 6.6+ 上继续叫它 "CFS" 已经不太准确；6.12 起 CFS 的旧代码被彻底移除。
💡 回到 OpenHarmony：同一个系统，跑 5.10 内核就是 CFS，跑 6.6 内核就是 EEVDF。做性能对比测试时必须先确认内核版本，否则两组数据的调度行为根本不可比。

自测五问

1
LiteOS-M 有多少个优先级？多少个任务？
32 个优先级（0~31，0 最高）；最大任务数由 LOSCFG_BASE_CORE_TSK_LIMIT 决定（常见 256）。这两个数字别混。
2
为什么位图置位要用 0x80000000 >> priority？
因为要用一条 CLZ 直接得到优先级。CLZ 数的是最高位起的前导零，所以最高位必须对应优先级 0；左移会让 CLZ 返回反过来的值。
3
任务被抢占后去了哪个状态？
回到 READY，仍在就绪队列里。只有 PEND / DELAY / SUSPEND 才真正离开就绪队列。
4
用信号量做互斥，会有什么隐患？
信号量没有优先级继承（LiteOS 的互斥锁才有），可能出现优先级反转：高优先级任务被中优先级任务间接拖死。
5
同一台 OpenHarmony 设备，调度行为可能不同吗？
会。Linux 5.10 基线用 CFS，6.6 基线用 EEVDF。性能测试前必须确认内核版本。
