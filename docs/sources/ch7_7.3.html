7.3 ArkUI 框架与渲染管线

7.2 讲到「首帧上屏」就停住了。本节接着往下：屏幕上那一个像素，是怎么从一句 this.count++ 变出来的。

ArkUI 的完整链路可以概括成四段：状态变更 → 标记脏节点 → 一帧内 Build / Layout / Draw（应用侧）→ RenderService 进程合成送显。源码分别在 foundation/arkui/ace_engine 与 graphic/graphic_2d。

理解这条管线最大的收获不是记住阶段名，而是明白两件事：① 改了数据不会立刻显示，要等下一个 VSync 节拍；② 应用进程只负责「生产绘制指令」，真正画像素的是另一个进程。这两条决定了绝大多数 UI 性能问题的成因与排查方向。

先更正原页面的三处表述

原版 7.3 只有一段五行的伪管线，其中三处容易让人建立错误的心智模型——尤其第一条，会让人把 ArkUI 当成 React 那类「虚拟 DOM 全树 diff」。

⚠️ ① 「组件树 diff」这个说法在 ArkUI NG 上已经不准确。NG 架构不是每次都拿新旧两棵树做对比，而是维护四类「脏节点队列」：谁变了就把谁标记进对应队列，下一帧只处理队列里的节点。
官方对这次演进的说法是：Diff 从「树对比」升级为单节点的函数式更新。
这也解释了为什么「减少嵌套」有效——它减少的是节点数与布局传播范围，而不是「diff 的树规模」。
⚠️ ② 「Render 树生成（渲染线程）」这个阶段在统一渲染下已经不存在于应用进程。
FrameNode 创建时就一直挂着对应的 RenderNode，Render 树不是每帧「生成」的；而真正的绘制（光栅化）在RenderService 进程里由 UniRender 一次完成。应用进程只把「这一帧改了什么」打包成命令发出去。
⚠️ ③ 整条链漏了最关键的驱动者：VSync。原图看上去像是「改数据 → 一路往下走 → 屏幕亮」。
实际上 ArkUI 不自定节拍：改数据只是「举手报名」，真正的推进要等窗口系统发来 VSync 回调。少了这一环，就解释不了「为什么改完数据到看见有一帧延迟」。

主线：改一个数字，要跨几道关

先看全貌。注意左侧标的是执行者——这条链上有两个进程、至少四个线程参与。

【应用进程 · UI 线程】 this.count++ # ① 赋值，触发观察者 │ ├─ 标记脏节点 # ② 按类型进不同队列 │ property / custom / layout / render │ └─ RequestFrame() # ③ 向窗口系统「报名」要一帧 │ ⋮ （等硬件 VBlank，可能等 0~16.7ms） ▼ 【应用进程 · UI 线程】FlushVsync(ts, frameCount) ├─ FlushBuild 重跑脏组件的 build() # 最多迭代 3 次 ├─ FlushLayoutTask measure / layout ├─ FlushRenderTask 同步属性到 RenderNode └─ FlushMessages 攒了一帧的命令打包 │ ▼ RSUIDirector::SendMessages → 跨进程 IPC 【RenderService 进程 · RS 主线程】 ├─ ProcessCommand 消化应用发来的事务 ├─ Animate 步进属性动画 ├─ Render 遍历全局渲染树 UniRender └─ OnUniRenderDraw 交给 RSUniRenderThread │ ▼ 【RenderService 进程 · UniRender 线程】 GPU 光栅化 → 合成所有窗口图层 → 帧缓冲 │ ▼ 下一个 VBlank 切换帧缓冲 → 屏幕
🏭应用进程
只生产指令：算布局、记属性变化。不画像素。
🎨RS 进程
只消费指令：遍历、光栅化、合成。全系统所有窗口一起画。
⏱VSync
唯一的节拍源。两端各自订阅，靠相位差形成流水线。

VSync：为什么要等，而不是立刻画

这是全节最该建立的一个直觉：「改数据」和「画面变化」之间必然隔着一帧。不是框架偷懒，而是屏幕的物理特性决定的——不等 VBlank 就写帧缓冲，会看到画面撕裂。

# 从硬件到应用的 VSync 分发链（rosen） 显示 HDI 收到硬件 VBlank │ hdi_screen.cpp: OnVsync 回调，喂时间戳 ▼ VSyncSampler 多次采样，校准出真实硬件节拍（容忍抖动） ▼ VSyncGenerator 依据采样建立软件 vsync 模型 ▼ VSyncController × 2 一个给 RS、一个给应用 │ ├─ RS 的相位 offset 更早 # 先让 RS 干活 └─ 应用的相位 稍晚 # 应用画「下一帧」，RS 合成「上一帧」

这个相位差是流水线的关键：如果两个进程同时开工，就变成「应用画完、RS 才开工」，一帧的实际耗时是两者相加；错开之后，两者并行，一帧的耗时约等于较慢的那一个。

环节由谁驱动不这么做会怎样
应用侧 build / layout应用自己的 VSync 回调无节拍地抢 CPU，耗电且抖动
RS 侧遍历与合成RS 的 VSync 回调（相位更早）与应用串行，一帧耗时翻倍
帧缓冲切换硬件 VBlank画面撕裂
💡 一个直接推论：60 Hz 屏上，一帧只有 16.7 ms。「掉帧」不是说这一帧花了 20 ms，而是它错过了这个 VSync，整体推到下一个节拍——用户看到的就是从 16.7 ms 变成 33.3 ms 的卡顿。
所以优化 UI 时的目标不是「平均快一点」，而是把最慢那一帧压进 16.7 ms 以内。

一帧之内，顺序是写死的

PipelineContext 是整个管线的协调者，核心方法只有一个：FlushVsync(nanoTimestamp, frameCount)。VSync 一到，它就按固定顺序把这一帧的任务跑完。

// frameworks/core/pipeline_ng/pipeline_context.cpp —— FlushVsync（简化） ProcessDelayTasks() // 延迟任务 DispatchDisplaySync() // 显示同步回调 FlushAnimation() // 动画步进 FlushBuild() // ← 重跑脏组件的 build() ├─ FlushFreezeNode() // 先解冻被临时冻结的节点 ├─ FlushDirtyPropertyNodes() // 应用 Node API 的属性改动 ├─ FlushPendingDeleteCustomNode() // 清理待删节点 └─ FlushDirtyNodeUpdate() // 重建自定义组件，最多迭代 3 次 taskScheduler_->FlushTask() // ← measure / layout FlushAnimationClosure() FlushMessages() // ← 把这一帧的命令发给 RS

三个值得注意的设计细节

细节为什么这么设计
属性改动要先于 build
（FlushDirtyPropertyNodes 在 FlushDirtyNodeUpdate 前）		通过 Node API 直接改的属性如果晚于 build 应用，会被 build 里算出的值覆盖。顺序反了就是「设了不生效」
build 最多只迭代 3 次
（maxFlushTimes = 3）		build 里改状态会产生新的脏节点，形成级联。留 3 次是给正常级联用，再多就说明状态在 build 里被反复改——那是设计问题，继续迭代只会死循环
先解冻再 build
（FlushFreezeNode）		被冻结的节点不参与更新；不解冻就 build，会出现「数据变了但这一帧没算进去」
⚠️ 「build 里不要改状态」不只是风格建议，是硬约束。build 中改 @State 会让框架在本帧内反复重建，超过 3 次就不再处理——表现为某些节点这一帧没更新，下一帧才补上，看起来像「偶发闪烁」，极难排查。

四类脏节点：不是一棵树在 diff

原页面用「组件树 diff」概括，但真实实现是四个独立的队列，各自在不同阶段被消费。分清它们，才知道「我这处改动会触发到哪一步」。

脏类型存放位置消费阶段触发方式
属性脏dirtyPropertyNodes_Build 之前Node API 直接改属性
自定义节点脏dirtyNodes_Build状态变更导致 build 需要重跑
布局脏taskScheduler_->dirtyLayoutNodes_Layout尺寸约束变化、节点增删
渲染脏taskScheduler_->dirtyRenderNodes_Render仅视觉属性变化（颜色、透明度）
冻结脏dirtyFreezeNode_Build 之前节点被冻结 / 解冻
✅ 这解释了一类常见现象：只改颜色为什么比重建组件便宜得多。改颜色只进「渲染脏」队列，跳过 Build 和 Layout，直接进 Render 阶段。而改一个影响尺寸的状态会连进三个队列。「改什么」比「改多少」更决定开销。

RequestFrame 只报一次名

// 任何一处标记脏节点，都会走到这里 AddDirtyLayoutNode(node); → 加入 dirtyLayoutNodes_ → hasIdleTasks_ = true // 表示「有活要干」 → RequestFrame() // 若本帧还没请求过，才真正向窗口系统要一帧

所以一次点击里改了 100 个状态，也只请求一帧——所有改动被合并到同一个 VSync 里处理。这就是「批量更新」的实现方式，不需要开发者手动 batch。

状态管理 V1 与 V2：粒度决定刷新范围

「最小更新域」这四个字原页面只写了一次，但它其实是整条管线的入口质量——脏节点标记得准不准，决定了后面所有阶段的工作量。而准不准，取决于用的是 V1 还是 V2。

维度V1V2
监听粒度对象引用级——深一层就够不着属性级——改多深都能捕获
刷新范围重新执行整个自定义组件的 build()只更新绑定该属性的 UI 节点
依赖收集运行期，代理对象通知编译期标记 + 渲染期收集
核心装饰器@State @Prop @Link @Observed @ObjectLink 等 7 种@ComponentV2 @ObservedV2 @Trace @Local @Param 等 6 种
数组只监听整体赋值；push / 改元素内属性常不刷新原生支持 push / splice / 子元素属性修改
典型坑改 user.name 界面不动，得整体换引用属性不加 @Trace 就完全不观察

V1 里想缩到字段级，有两条路

// 路线一：拆行组件 + @Observed / @ObjectLink（组件级 → 行级） @Observed class RowData { id: string = ''; count: number = 0; } @Component struct RowView { @ObjectLink item: RowData; // 接住同一实例，不是拷贝 build() { Text(`${this.item.count}`) } } // 路线二：再进一步，用 @Track 缩到字段（API 11+） @Observed class RowData2 { id: string = ''; @Track title: string = ''; // 只有读取 title 的 UI 会刷新 }
⚠️ V1 的 @ObjectLink 只代理一层。如果 RowData 里再嵌一个自定义类，改那个类里的字段 @ObjectLink 就管不到了，必须再拆一层组件、再给嵌套类加 @Observed。
这是 V1 最典型的「装饰器都加了但就是不刷新」的原因——不是写错了，是层级超出了一层代理的能力。

「最小更新」是怎么被写坏的

框架默认做的是最小更新，但下面五种写法会让它退化成大面积重建。这几种在真实项目里出现频率极高，而且都不会报错。

写法后果改法
一个大 ViewModel 装整个页面状态任一字段变化 → 整页重建按更新范围拆成多个状态变量 / 多个子组件
在 build() 里做计算或调函数每次重建都重算，可能还写状态前置到 aboutToAppear 或异步算好再赋值
@State 持有深层对象，直接改内部字段V1 下不刷新；用整体替换又整组件重建用 V2 的 @Trace，或 @Observed + @ObjectLink
ForEach 的 key 用 index 或时间戳key 不稳定 → 整行重建，图片闪烁用稳定的业务 ID 作 key
组件嵌套过深（十层以上容器）测量与布局沿层级传播，耗时长用 RelativeContainer 扁平化
💡 还有两个容易被忽略的：
① 大量重复子项用自定义组件会额外产生 CustomNode，改用 @Builder 不生成额外节点，节点数与内存都更低。
② 长列表里频繁创建销毁的项加 @Reusable，滑出可视区进复用缓存、滑入时调 aboutToReuse 刷新——省的不只是创建开销，还有 GC。

布局：成本不在代码，在传播

Layout 阶段是唯一会沿树传播的阶段：父的约束变了，子要重新测量；子的尺寸变了，父可能要重新摆放。这是「深层嵌套为什么慢」的根源。

# 一次布局的传播方向 父节点约束变化 → measure（向下传约束，向上返回尺寸） → 子树逐层重新测量 → layout（向下传最终位置） # 所以：改一个内层组件的尺寸 # 可能让整条祖先链重新测量 # 而改一个纯视觉属性（颜色）不碰布局
容器选择适用与代价
Row / Column最轻，单一方向布局。能用就别上 Flex
Flex灵活但测量成本更高（需处理换行、剩余空间分配）
RelativeContainer扁平化利器——多层嵌套的定位关系统统拍平到一层
Grid / List / Swiper专为大量子项设计，配合 LazyForEach 才有意义
✅ 判断「该不该扁平化」的实用标准：如果几层容器只是为了控制位置（对齐、间距、居中），而不是真的需要独立的布局语义，那它们几乎都可以被 RelativeContainer 或统一的 padding/margin 替掉。每一层省下的是整棵子树的测量。

统一渲染：应用只出指令，RS 一口气画完

这是 OpenHarmony 图形栈与早期 Android 最本质的差别，也是「应用进程不画像素」这句话的由来。

环节OpenHarmony（统一渲染 UniRender）Android（分离渲染，传统模型）
绘制应用只提交命令，RS 进程遍历全局渲染树时统一做应用进程的 RenderThread 先画到自己的 Surface
合成同一个进程、同一次遍历里完成SurfaceFlinger 再合成一遍
帧缓冲省掉中间那一份各应用 Surface + 合成输出，多一份开销
跨窗口效果天然可见全系统图层（模糊背景、跨窗口动效更容易做）拿不到别的窗口内容

RS 主线程一帧的主循环

// rosen/modules/render_service —— 每帧主循环（简化） ConsumeAndUpdateAllNodes() // 同步应用侧节点状态 ProcessCommand() // 消化应用发来的事务 Animate(timestamp) // 步进属性动画 CollectInfoForHardwareComposer() Render() // 遍历全局渲染树（UniRender） OnUniRenderDraw() // 交给 UniRender 线程做 GPU 光栅化 SendCommands()
⚠️ RS 进程的调度优先级是刻意拉到最高的（实时调度策略）。因为它管的是全系统所有窗口的合成——它卡一帧，不是某一个应用卡，而是整个屏幕都在卡。这也是为什么「某个应用把 RS 拖慢」会影响其他应用的观感。

掉帧了，该看哪里

管线分四段，掉帧也可能发生在任意一段。先定位在哪一段，再谈优化——否则很容易在应用代码里找半天，问题其实在合成侧。

现象最可能卡在下一步查什么
滑动时列表卡，静止不卡Build 或 Layout（应用侧）是否有整行重建、key 是否稳定、是否用了 LazyForEach
点一下延迟一下才变没等到下一帧，或主线程被占点击回调里有没有同步重活；是否在等网络
动画掉帧但列表不卡RS 侧合成图层数是否过多、是否有大面积模糊 / 离屏渲染
偶发闪烁、部分节点不更新build 内改状态导致迭代超限检查 build() 里是否有赋值
所有应用一起卡RS 进程被拖慢hidumper -s RenderService 看节点数与帧率

两个能直接用的工具

# ① DevEco Studio 的两条泳道（最有用） ArkUI State // 哪个状态变量变化最频繁、影响范围多大 ArkUI Component // 哪个组件被绘制了多少次、单次多长 # ② 设备侧看合成器状态 hdc shell hidumper -s RenderService
💡 「ArkUI Component 泳道里某个组件被绘制了几十次」是最好用的信号。正常情况下静止页面应该接近 0 次；如果它在反复重绘，几乎一定是某个状态变量在无意义地变（时间戳、随机数、每帧更新的对象），或者它依赖了过大的状态。

五个常见误解

1️⃣「改完状态界面就该立刻变」
不会。必须等到下一个 VSync，而且这一帧不一定来得及——错过就推到下一帧。
2️⃣「ArkUI 在做虚拟 DOM diff」
NG 架构是脏节点队列 + 单节点更新，不是新旧树对比。所以「减少嵌套」省的是布局传播，不是 diff 规模。
3️⃣「应用进程负责把界面画出来」
统一渲染下应用只生产指令。光栅化与合成都在 RS 进程。
4️⃣「帧率上不去就是代码写得不好」
可能卡在合成侧（图层过多、离屏渲染）。先分段定位，别默认是应用代码。
5️⃣「V2 一定比 V1 快」
V2 的更新粒度更细，但属性不加 @Trace 就完全不观察；V1 在结构简单时反而更省心。不能在同一状态链里混用两套。
✅ 本节与《应用开发》的分工：应用课讲「怎么写出不卡的界面」（装饰器怎么用、组件怎么选）；本节讲「为什么这些写法会不卡」——从 PipelineContext 与 RenderService 的视角看同一件事。
系统课的价值在于：当应用课给的规则失效时（比如某个偶发闪烁），你能顺着管线自己找到原因。

自测五问 & 第 7 章收尾

问题要点
1. 改状态后为什么不会立刻显示？要等窗口系统下发 VSync；RequestFrame 只是报名
2. 一帧内 Build 和 Layout 谁先？Build 先（且属性脏在 build 前应用），然后 FlushTask 做 measure / layout
3. 只改颜色会走几个阶段？只进渲染脏队列，跳过 Build 与 Layout
4. 为什么 RS 的 VSync 相位要更早？让「应用画下一帧」与「RS 合成上一帧」并行，避免串行翻倍
5. 统一渲染省掉了什么？应用侧 RenderThread 的绘制 + 一次中间帧缓冲
